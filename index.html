Part I

Application Layer & Transport Primitives

The network edge, client-server abstractions, naming systems, security handshakes, and transport layer multiplexing.

01

Protocol Layering & Encapsulation

The global Internet functions via modular abstractions. Rather than building a single monolithic system, protocols are organized into a 5-layer stack:

Application Layer (L5)
Generates messages (HTTP, DNS, SSH, TLS). Payload Unit: Message.
Transport Layer (L4)
Provides process-to-process communication, port addressing, and reliability (TCP, UDP, QUIC). Payload Unit: Segment.
Network Layer (L3)
Routes datagrams across autonomous systems via logical IP addressing (IPv4, IPv6, BGP, OSPF). Payload Unit: Packet / Datagram.
Data Link Layer (L2)
Transfers frames between adjacent nodes on the same physical link (Ethernet, Wi-Fi 802.11). Payload Unit: Frame.
Physical Layer (L1)
Transmits raw binary bits across physical media (Copper twisted pair, Fiber optics, RF radio). Payload Unit: Bits.

02

DNS: The Internet's Distributed Phonebook

Humans memorize domain names (github.com); routers understand 32-bit or 128-bit IP addresses. The Domain Name System (DNS) is a hierarchical, distributed database that translates human names into machine routable addresses.

DNS over HTTPS (DoH) & DoT

Traditional DNS queries travel over plaintext UDP port 53, allowing ISPs and surveillance middleboxes to eavesdrop on every site you visit. Modern DNS over HTTPS (DoH, RFC 8484) encrypts queries inside TLS 1.3 sessions over port 443.

03

HTTP Evolution: HTTP/1.1 to HTTP/3 (QUIC)

HTTP has undergone three architectural revolutions. While HTTP/1.1 was limited to serial FIFO requests and HTTP/2 multiplexed streams over a single TCP socket, both suffered from Head-of-Line (HOL) blocking:

  • HTTP/1.1 Pipelining: A slow request at the head of the queue blocks all following responses. Browsers worked around this by opening 6 parallel TCP connections per domain.
  • HTTP/2 TCP HOL Blocking: Solved application-layer blocking by framing requests into binary streams over 1 TCP socket. However, if one packet is dropped on the wire, the kernel pauses all streams until TCP retransmits it.
  • HTTP/3 QUIC over UDP: Replaces TCP entirely with QUIC in userspace over UDP. Each stream has independent flow control; losing a packet on Stream 1 has zero impact on Streams 2 and 3!

04

TLS 1.3: Cryptographic Handshake & 0-RTT

Transport Layer Security (TLS) secures the public web against eavesdropping and tampering. TLS 1.3 radically simplified cryptography by deprecating insecure algorithms (MD5, SHA-1, RC4, RSA key exchange) in favor of ephemeral Diffie-Hellman (ECDHE).

TLS 1.2 Handshake = 2 RTTs (TCP + 2 TLS flights) TLS 1.3 Handshake = 1 RTT (ClientHello sends ECDHE key_share immediately)

05

Sockets & Transport Demultiplexing

Operating systems multiplex thousands of network connections onto a single network interface card (NIC). The kernel routes incoming packets using the Socket 4-Tuple:

Socket 4-Tuple = (Source IP, Source Port, Destination IP, Destination Port)

06

UDP vs. TCP: The Fundamental Trade-off

The transport layer offers two primary paradigms: connectionless datagrams (UDP) or reliable in-order byte streams (TCP):

User Datagram Protocol (UDP)
No connection setup, no retransmissions, no congestion control. 8 bytes fixed header. Packets may arrive out-of-order, duplicated, or not at all. Ideal for real-time voice, video, DNS, and QUIC.
Transmission Control Protocol (TCP)
Full-duplex, point-to-point, reliable byte stream. Tracks sequence numbers, acknowledgments, dynamic sliding windows, and adapts to network congestion.

07

Reliable Data Transfer (rdt) & Sliding Window

How do we build reliable communication over an unreliable physical channel? Stop-and-Wait protocols are inefficient because they waste bandwidth waiting for acknowledgments. High-performance protocols use a Sliding Window:

Analogy

Stop-and-Wait is sending a single letter and waiting for a reply by mail before writing the next. A sliding window is mailing 10 numbered letters at once, advancing your sending clipboard every time a reply arrives.

Part II

TCP & Congestion Control

Connection lifecycles, flow control buffers, round-trip estimation, network collapse prevention, and modern BBR pacing.

08

TCP Connection Lifecycle: The 3-Way Handshake

Before exchanging bytes, TCP synchronizes Initial Sequence Numbers (ISNs) using a 3-way handshake, and gracefully tears down using a 4-way exchange:

  1. SYN: Client chooses random ISN_c and sends [SYN, Seq=ISN_c]. Enters SYN_SENT.
  2. SYN-ACK: Server chooses ISN_s and replies [SYN+ACK, Seq=ISN_s, Ack=ISN_c + 1]. Enters SYN_RCVD.
  3. ACK: Client acknowledges server ISN [ACK, Ack=ISN_s + 1]. Both enter ESTABLISHED.

09

TCP Flow Control: The Receive Window (rwnd)

Flow control prevents a high-speed sender from overwhelming a slow receiver's socket buffer. The receiver advertises its available buffer space in the Window field of every TCP header:

Available Receive Window: rwnd = RcvBuffer − [LastByteRcvd − LastByteRead] Sender Constraint: LastByteSent − LastByteAcked ≤ rwnd

10

RTT Estimation & Retransmission Timeout (RTO)

How long should TCP wait before declaring a packet lost? Setting RTO too low triggers bogus retransmissions; setting RTO too high causes long recovery stalls. TCP uses Jacobson's Algorithm (RFC 6298) with Exponentially Weighted Moving Averages (EWMA):

SRTT = (1 − α) · SRTT + α · SampleRTT (α = 0.125) RTTVAR = (1 − β) · RTTVAR + β · |SRTT − SampleRTT| (β = 0.25) RTO = SRTT + 4 · RTTVAR

11

TCP Congestion Control: Reno & Cubic

While flow control protects the receiver, congestion control protects the intermediate network from collapse. TCP probes for available capacity by dynamically adjusting its Congestion Window (cwnd):

Effective Transmission Window = min(cwnd, rwnd)

Classic TCP Reno uses Additive Increase, Multiplicative Decrease (AIMD): increase cwnd by 1 MSS per RTT, and halve it on packet loss. Modern Linux default TCP CUBIC uses a cubic polynomial curve to scale rapidly over high-bandwidth links.

12

Bufferbloat & Google BBR

Cheap memory in consumer routers led to bufferbloat: routers buffer gigabytes of packets rather than dropping them. Loss-based algorithms (Reno, Cubic) fill these buffers completely, spiking network latency from 20ms to 2,000ms:

Google BBR (Bottleneck Bandwidth and RTT)

BBR does not treat packet loss as a congestion indicator. Instead, it measures maximum delivery rate (BtlBw) and minimum round-trip time (RTprop) simultaneously, maintaining maximum throughput while preventing queue buildup.

13

SYN Flood Attacks & SYN Cookies

In a SYN Flood DDoS attack, an attacker floods a server with thousands of TCP SYN packets with forged IP addresses and never replies to the SYN-ACK. The server's backlog queue fills up, exhausting kernel memory:

Part III

The Network Layer & Routing

IP addressing, subnetting, NAT translation, IPv6, router data planes, and autonomous system routing protocols.

14

IPv4 Addressing, Subnetting & CIDR

An IPv4 address is a 32-bit integer divided into two components: the Network Prefix and the Host Number. Classless Inter-Domain Routing (CIDR, RFC 1519) eliminated rigid Class A/B/C allocations in favor of flexible prefix lengths:

Total Host Addresses = 2^(32 − Prefix_Length) Usable Host Addresses = 2^(32 − Prefix_Length) − 2 (Excludes Network & Broadcast)

15

Network Address Translation (NAT)

To survive IPv4 exhaustion, home and enterprise routers use Network Address Port Translation (NAPT). Multiple devices share a single public WAN IP by mapping private RFC 1918 addresses to unique ephemeral source ports:

  • 10.0.0.0/8 (10.0.0.0 to 10.255.255.255) — Large enterprise networks
  • 172.16.0.0/12 (172.16.0.0 to 172.31.255.255) — Medium networks, Docker default
  • 192.168.0.0/16 (192.168.0.0 to 192.168.255.255) — Home routers and LANs

Network Latency Numbers Every Engineer Must Know

Software architectures cannot violate the laws of physics. Light in vacuum travels at $300,000\,\text{km/s}$, but inside silica glass optical fiber ($n \approx 1.5$), signal propagation is strictly limited to ~200,000 km/s (5 µs per kilometer):

  • Datacenter Same-Rack RTT: ~0.1–0.25 milliseconds (100–250 µs).
  • Cross-Datacenter Availability Zone (AZ): ~1–2 milliseconds.
  • San Francisco to New York: ~41.4 ms physical fiber minimum (real-world: ~70 ms).
  • New York to London (Transatlantic): ~55.7 ms physical fiber minimum (real-world: ~78 ms).
  • San Francisco to Tokyo (Transpacific): ~82.8 ms physical fiber minimum (real-world: ~115 ms).
  • Geostationary Satellite (GEO) RTT: ~500–600 milliseconds (35,786 km orbit each way).
  • Low Earth Orbit (Starlink / LEO) RTT: ~25–45 milliseconds (550 km orbit).
